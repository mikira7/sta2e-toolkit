What Concept D has to keep working

Working task card. Every block the card can render has a place in the design: the crew dice and their heading, named assist dice, the Attack Pattern die, ship dice with the Advanced Sensor Suites and Communications Officer notes, every note strip (warning, note, bonus, traits), the four readouts plus Complications, Spent and Gained tokens, Pending Assists, Make Your Own Luck, the reroll grid with cost lines, Edit Results, Succeed/Hit at Cost, Confirm/Resolve, Add to Pool, Completed, and the assist roll's "Add to Task Roll →" and "Applied to". It works for player, NPC (Threat), ground and ship rolls, because those change the words on the card, not its layout.

Wiring the build must not break:

  • Each die stays a .sta2e-card-die with data-pool/data-index and a real d20 <img> inside. setCardDieState paints selection by changing that image's opacity and filter, so a CSS background image would leave selected dice looking unselected. The first mockup drew the d20 that way. The cards above now use the real markup, and the selected die (14, on the armed card) is painted the way that function paints it.
  • The button classes stay: sta2e-player-reroll, sta2e-make-own-luck, sta2e-player-assist-roll, sta2e-edit-roll-card, sta2e-succeed-at-cost, sta2e-player-confirm, sta2e-assist-to-roll and sta2e-add-to-pool. So do the sta2e-rr-name/sta2e-rr-cost spans and data-filled="1", which makes an armed key light up instead of looking disabled.
  • Every action group stays inside its own .sta2e-working-actions--* wrapper. The render hook deletes those wrappers for players who are not the roller, and the reroll tray is appended to the closest one. That is why the reroll grid goes on the inner .sta2e-task-rerolls and not on the wrapper.
  • The colours that _armCardSelection rewrites while a reroll is armed (background, border colour, text colour, opacity) stay inline on the keys and never go in the stylesheet. The raised-key bevel is a box-shadow, which that function doesn't touch, so armed keys keep their 3D look.
  • The card gets no inline border-radius, just like the TNG frame.

Other chat cards. All of them go through lcarsChatCard, so Concept D would add one TOS path there: the housing and header lamps around the card, with the body passed through untouched. That keeps the momentum spend panel's placement before .sta2e-damage-controls, the root classes the tracker looks for, and the five render hooks. One caveat: the bodies set their own colours and buttons inline, in the TOS amber. So the build needs a step like unroundButtons that strips the inline background and border from body buttons, otherwise those buttons stay flat outlined ones instead of raised console keys. The mockups above assume that step. The CRT screen with scanlines goes only behind readout rows. Sliders, checkboxes and target lists sit on the plain panel, where scanlines would make them harder to use.

Out of scope, as with TNG: the warp navigation cards and the star-system reports keep their own skins.

How any of these would be built

The TNG frame already works this way, so the TOS version would copy it. The renderer adds one class, such as sta2e-task-card--tos, when the theme is tos-panel. Shape goes in styles/task-card.css and styles/chat-card.css, and colour stays inline. On the other cards, lcarsChatCard would gain a TOS path next to its legacy thunk, and every card lcarsCard builds would pick it up. None of this touches the dice selection, the reroll tray or the momentum-spend hooks, because the frame wraps the body and does not rebuild it.

Things to check per concept: A and C need the inline border-radius on buttons stripped, the same way unroundButtons does now. B's dice show as text, so the clickable .sta2e-card-die spans need a bracket skin rather than the d20 image. C's division colour needs a category on each card (command, sciences or operations), and right now nothing records one.
